# 云端派工推荐做法

云端已生成需求、设计、验收标准，要下发到 Atlas CLI 执行，并在完成后收回执。ACP **没有**「云端直接推文件」的 RPC，不要走 `fs/write_text_file`（那是 Agent 让浏览器写盘）。

正确拆成三步：把文档变成 Agent 工作区里的 **Documents Contract**，再用 `session/prompt` 开工，最后用 **约定回执** 收回结果。`POST /atlas/v1/task-reports` 只是遥测（成功、耗时、artifact 路径），**不是**验收回执。

本做法第一版只动 `atlas-relay-demo`，不改 CLI、不改 atlas-server。术语见 [CONTEXT.md](../CONTEXT.md)。

## 文档落到哪里

| 云端文档 | 写入 CLI 仓库（Documents Contract） |
|---|---|
| 需求 | `documents/requirements-analyst/<jobId>-requirements.md` |
| 设计 | `documents/detailed-design/<jobId>-detailed-design.md` |
| 验收标准 | `documents/test-cases/<jobId>-acceptance.md` |
| 执行回执 | `documents/execution-report-<jobId>.json` |

`standard` 模式下，有 `documents/detailed-design/` 就可以直接实现。验收标准应写成可执行检查（命令 + 期望），否则 Role 4 只能口头「符合设计」。

## 总流程

云端（或本 demo 聊天页）当 **ACP Client**，目标机器上的 `atlas agent headless` 当 **Relay Agent**。

```
云端生成 3 份文档（可下载的 http(s) URL）
    │
    ▼
选中 Bound Agent（agent_id）
    │  session/new(cwd=业务仓根)
    │  session/prompt ① Documents Drop
    ▼
CLI 按 URL 拉取，写入 documents/…
    │  session/prompt ② Role 4 Run
    ▼
Task 拉起 atlas-sdd:4-software-engineer-agent
（不跑 Role 1/2/3，不用整段 /implement；Role 4 内用 tdd）
    │  session/prompt ③ Execution Report
    ▼
写出 execution-report JSON，Client 解析 status / summary
```

三轮都带同一个 **jobId**，落盘路径、实现、回执才能对上。

## 三轮分别做什么

### 1. 下发（Documents Drop）

文档走 **URL**，不把正文塞进 prompt。Agent 用 curl / web_fetch 下载后 `write` 到上表路径。这一轮禁止写业务代码。

- 文档大、或云端已有对象存储：给短时签名 URL。
- 本机打通：可用 demo 自带示例  
  `http://127.0.0.1:2420/sample-docs/{requirements,design,acceptance}.md`  
  源码在 `web/sample-docs/`，打进 exe。跑 CLI 的机器必须能访问这些 URL。

`POST /dispatch/prompts` 只生成三轮文案，不替 Agent 拉网。

### 2. 执行（Role 4 Run）

文档已在盘上之后再发第二轮。只拉 `atlas-sdd:4-software-engineer-agent`（`run_in_background: false`）。

- cwd 必须是**业务仓根**，且已装 `atlas-sdd`。
- headless 加 `--always-approve`，否则会卡在权限。
- 一轮 `session/prompt` 可能很长；以第三轮回执为准，不要只看第一段模型输出。

### 3. 反馈（Execution Report）

`session/prompt` 返回只表示**这一轮结束**，不是「项目做完」。约定 Agent 写出机器可读文件，例如：

```json
{
  "jobId": "pay-20260901",
  "status": "passed",
  "summary": "…",
  "changedFiles": ["README.md"],
  "tests": {
    "command": "rg -n \"Atlas Relay Demo\" README.md",
    "exitCode": 0,
    "logExcerpt": "…"
  },
  "acceptance": [
    { "id": "AC-1", "result": "pass", "evidence": "README.md 存在" }
  ]
}
```

`status` 为 `passed` | `failed` | `blocked`。页面从最后一条 Agent 消息里解析 JSON；解析失败则去仓里读 `documents/execution-report-<jobId>.json`。

过程日志继续听 `session/update`。Task Report 可旁路看 `success` / `artifacts` / `error`，不能当验收。

## 和「改 atlas-server 做任务队列」的差别

| | 现在（relay-demo） | 以后 |
|---|---|---|
| 触发 | 云连上指定 Agent，连发 3 轮 prompt | `POST /jobs`，Agent 领取 |
| 下发 | URL 拉取 | 对象存储 + job 附件 |
| 回传 | 约定 `execution-report.json` | `POST /jobs/{id}/complete` |
| 多机 | 已有 `agent_id` 选择 | 按仓库/标签调度 |

第一版不必动 atlas-server；队列、重试、鉴权适合第二期。

## 落地检查

- [ ] Bound Agent 在线，cwd 为业务仓且可写 `documents/`
- [ ] 三份 URL 为 http(s)，Agent 机器能访问
- [ ] 业务仓已启用 `atlas-sdd`，Role 4 能被 Task 拉起
- [ ] CLI：`atlas agent --always-approve headless --grok-ws-url …?agent_id=…`
- [ ] 回执文件存在且 `jobId` 与派工一致
