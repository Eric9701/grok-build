## 一、生产日志中正在发生的问题（有日志实证）

**1. 物化表定时刷新每半小时批量失败（8/5 至今持续）**
`logs/level_all_json.2026-08-*.json` 里 `ads_kfc_mkt_gift_card_dmj0106/dmj0107/dmj`、`ads_kfc_mkt_giftFY03awhb` 等表每次调度都报 `BadSqlGrammarException`。根因是库里存的 `sqlContent` 本身是坏的——执行时 SQL 变成了 `from ads_kfc_mkt_gift_card_sell_daywhere part_dt >= '2026-01-15'and part_dt <= '2026-01-15'order by part_dt`（**表名与 where、日期与 and 之间缺空格**），而且日期冻结在 1 月 15 日。`TzCustomTableServiceImpl.saveCustomTable` 保存 SQL 时**完全不做校验**，坏 SQL 入库后调度器永远重试、永远失败、刷爆日志。

**2. “分区为空”错误**：`insertSRDataWithCreateTime` 把 `create_time` 写成 `refreshDate` 字面量，补数传历史日期（如 1/15）时落在动态分区窗口 `[-60, +30]` 天之外，StarRocks 直接报 "data cannot be inserted into table with empty partition"。

## ❌ 改出的问题（建议立即修）

**前端 `visible` 字段传了布尔值，和后端类型不匹配，会把保存接口改坏**

改动让 `AddIndicatorDialog`/`AddWeiDuDialog` 的 `formData.visible = true`（布尔），提交时 `visible: formData.visible ?? true`。但我核对了后端：

- `TzMetricDto.visible` / `TzDimensionDto.visible` / 实体 `TzMetric.visible` 全是 `String`
- 建表语句（`tz_common_dimension.sql:8`）是 `visible char(1) DEFAULT '1'`
- 所有消费处都是字符串比较：`"1".equals(visible)`、`StrUtil.equals("1", each.getVisible())`

前端传 `true` → Jackson 会把 JSON 布尔转成字符串 `"true"` → 写 `char(1)` 列时要么报 `Data too long`（严格模式）要么截断成 `'t'`；之后所有 `"1".equals(...)` 判定都是 false，**指标/维度保存后变成“不可见”**，影响所有新增和编辑。

顺带说明：原来的 bug（`visible: undefined`）实际危害很小——字段缺失后 MyBatis-Plus 的 updateById 默认忽略 null 字段，insert 走列默认值 `'1'`，编辑时原值会被保留。这次的“修复”反而是把没大碍的问题变成了真故障。

**修法**：三处布尔全部改回字符串——子组件默认值 `visible: '1'`，编辑回填 `formData.visible = String(props.editingRow.visible) === '1'`（或 `props.editingRow.visible ?? '1'`），父组件提交 `visible: formData.visible ?? '1'`。

## ⚠️ 只修了一半 / 有兼容性风险

**1. 指标列表翻页高亮仍会回跳第 1 页**：请求参数 `res.current → res.pageNum` 改对了，但列表返回对象（`index.vue:1460`）仍然没有 `pageNum` 字段。`useDataSource.ts:113` 拿 `res.pageNum`（undefined）回写分页状态，数据翻页正确但分页组件高亮回到第 1 页。返回值补一行 `pageNum: response.current || pageNum` 即可（维度加载 1392 行同样）。

**2. Python 基础查询路径的 where 白名单可能拒绝两种既有写法**：新加的校验白名单只有 `dimensions + 指标名 + part_dt`（与另两条路径一致，方向正确），但：
- `where store_code = 'x'` 而 `store_code` 不在本次 `dimensions` 分组里 → 拒绝。之前这种“只过滤不分组”的查询是能通过的；
- 带表名前缀的写法 `where t1.store_code = 'x'` → `t1` 不在白名单，也会被拒。而基础路径的代码本来专门支持这种写法（会自动补前缀、转 keywordId）。

如果有调用方在用这两种写法，升级后会从“能查”变成报错。建议把指标可用的维度列（而非仅本次分组列）加进白名单，并在 token 扫描时跳过 `.` 前面的表名部分。

**3. 非法时间格式的报错语义**：`resolve_time_bound` 从“原样透传”改成抛 `ValueError` 是对的（堵注入），但 `http_server_db.py` 没有对应的 `except ValueError → 400`，用户传错格式会得到 500“请联系管理员”。行为可接受，建议后续补 400。
