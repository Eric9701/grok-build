# 人员技能评定口径

权威叙述：`docs/ppt/企业级系统开发-Atlas素材.md` §20–25。这里只写 **Task Report 能算什么**。阈值是示例，试点后用团队中位数校准。

## 原则

1. **多证据，少单指标** — 成功率、角色覆盖、产物类型、评审痕迹、周期一起看。
2. **对岗位，不对「会不会用 AI」** — 需求岗看 Role 1 + 文档；开发岗看 Role 4 + 代码产物 + 评审。
3. **先走对流程，再看快不快** — 该走企业链却跳门闩的高产，企业场景记负分。
4. **匿名/缺字段降权** — `anonymous`、空 `model`、空产物不参与排名。
5. **指标筛人，专家校准** — 默认不读 prompt；用户要求抽检时再 `--include-sensitive` 或读 `documents/`。

## 角色名映射

Task Report 的 `subagentType`（现网常见，含无前缀别名）：

| 语义 | 匹配 |
|---|---|
| 主会话 plan | `grok-build-plan`、`grok-build:plan` |
| 探查 | `explore` |
| Role 1 需求 | `atlas-sdd:1-requirement-analyst-agent`、`1-requirement-analyst-agent` |
| Role 2 架构 | `atlas-sdd:2-architect-design-agent` |
| Role 3 详设 | `atlas-sdd:3-program-design-agent` |
| Role 4 实现 | `atlas-sdd:4-software-engineer-agent`、`4-software-engineer-agent` |
| Role 6 测试 | `atlas-sdd:6-qa-engineer-agent` |
| 双轴评审 | `description` 含 `双轴评审` / `Spec 轴` / `Standards 轴` / `code-review`（两轴分开计，不合并排序） |

`parentSessionId` 非空时，同一父会话近似一个 **需求包**。否则只报用户级角色覆盖，不编完成率。

## 五维（默认权重）

岗位未指定时用全栈权重。缺数据的维标「不足」，**不要**按权重硬凑总分。

| 维 | 权重 | Task Report 映射 | 高分样子 |
|---|---|---|---|
| A 流程纪律 | 25% | 角色覆盖；父会话是否 1→3→4（strict 再 6）；plan/explore 占比 | 该走链时不跳步 |
| B 并行效率 | 25% | 同一时刻重叠的子代理任务：峰值并行度、并行占比、时间加权平均并行度 | 会拆子代理并行（峰值 ≥ 2），不是全天串行排队 |
| C 领域深度 | 15% | Role 1/3 任务数与 doc 产物 | 有需求/详设任务且留下 doc |
| D 工程效率 | 20% | `durationMs`、`turns`、`toolCalls`、空转指数 vs 团队中位 | 同等角色下更短、更少空转 |
| E 工具熟练 | 15% | `clientVersion`、plan vs explore、Catalog 集中度 | 版本新、会用工兵角色、模型不散乱 |

**岗位切片（加重，不是只看一维）：**

- 需求分析：A + C
- 软件开发：B + D（并行拆任务 + 少空转）
- 架构：只统计明确 Role 2；**不因没出架构扣分**
- QA：Role 6 覆盖 + 评审 Standards 痕迹
- 全栈/骨干：五维均衡，且能区分小改动路径与企业链

维内档：证据明显偏高/中/低，或不足。可附 1–5 分，但必须能回溯到上表字段。

## B 并行效率算法

只统计 **同一 Report User** 的子代理任务（多人则每人各算一遍）。两条任务「同一时间并行」= 时间窗相交。

**时间窗** `[start, end)`：

1. `start` = `startedAt`，缺则 `createdAt`
2. `end` = `completedAt`，缺则 `start + durationMs`
3. 解析失败、或 `end <= start` 的行丢弃；有效窗 < 2 则本维 **不足**（无法谈并行）

**扫线：** 把每条窗拆成 `+1` at `start`、`-1` at `end`，按时间排序（同一时刻先 `-1` 后 `+1`，避免首尾相接算重叠）。从左到右累加 `active`。

| 指标 | 计算 |
|---|---|
| **峰值并行度** | `max(active)` |
| **并行任务数** | 至少与另一条窗相交的任务条数 |
| **并行占比** | 并行任务数 / 有效窗任务数 |
| **平均并行度** | 仅在 `active ≥ 1` 的时段，对 `active` 做时长加权平均 |

全串行：峰值 = 1、并行占比 = 0。高分：峰值 ≥ 2 且并行占比明显（会同时跑多个子代理）。不要把「一天 48 条但互不重叠」当成并行。

## 评分卡（示例阈值）

对某用户、某区间。分母为该用户任务数，除非另写。

| 指标 | 计算 | 示例阈值 |
|---|---|---|
| 企业链完成率 | 含 Role 1 且后续同父会话有 3、4 的包 / 含 Role 1 的包。无父会话则改报「角色覆盖：是否出现 1/3/4」 | ≥ 80% |
| 任务成功率 | `successCount / count` | ≥ 70% |
| 文档产物比 | kind=doc 的产物 / 需求与设计类任务的产物；无 1/3 任务则 N/A | ≥ 90%（角色 1/3） |
| 代码产物比 | kind=code / 实现类（Role 4 或 plan 且有 code） | ≥ 90%（角色 4） |
| 空转指数 | `tokensUsed / max(artifactCount,1)` ÷ 团队中位数（overall 各用户同样公式，排除 anonymous） | ≤ 1.5× |
| 峰值并行度 | 扫线 `max(active)`，见上节 | ≥ 2 |
| 评审债 | 有双轴评审痕迹的实现次数；硬违反需抽检，默认「未抽检」 | 趋近 0 |
| 模型合规 | 已分配 catalog id 的任务占比。**无分配表则不写此行**，只写实际 Catalog 分布 | 100% |

派生（组织层，多人必写）：规范遵循率 / 文档覆盖率 / 评审闭环率 / 单位产物 Token / 运行时新鲜度，见 PPT §20。现网用明细近似，不要假装有独立需求包表。

## 质量误读

| 看起来 | 可能含义 | 不要直接结论 |
|---|---|---|
| 峰值并行高 | 会拆子代理，或拆太多空转 | 一定高效 |
| Token 高、产物少 | 空转或调研 | 一定低效 |
| 成功率低 | 环境/权限/任务过难；或 plan 把中断标成 error | 一定能力差 |
| 取消多 | 需求变了或门闩拦住 | 一定不认真 |
| 只有 explore/plan、没有 Role 1/3 | 跳过企业链 | standard 小改动可能合理 |
| 产物 kind=doc 多、code 少 | 停在设计 | 可能卡在评审或等待决策 |
| description 全是 `<user_query>` | 上报口径 | 主题/评审债数据不足 |

失败成簇且 description 为 `<user_query>` 时，先记上报问题，再谈个人。

## 等级（建议，非 HR 结论）

- **L1 试用：** 会登录痕迹（有成功任务）、在用 Atlas
- **L2 独立开发：** 小功能路径闭环（plan/实现有成功 + 代码产物），无证据表明评审硬违反
- **L3 企业交付：** 窗口内出现 1 与 3 与 4（strict 再加 6），且有 doc/code 产物
- **L4 教练：** 五维均衡、空转低于团队中位、角色分布能带人（多种 Agent 且链完整）

给等级时写清：依据哪些评分卡格子；缺格则只给「至多 Lx」或「不够定级」。
